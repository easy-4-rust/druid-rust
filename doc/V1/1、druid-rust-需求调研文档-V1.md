## 2. 调研范围

V1 调研聚焦三类典型用户：

1. **Web 后端开发者**：用 axum / actix-web 写 HTTP 服务，需要数据库连接治理。
2. **后台 worker**：用 tokio + cron 跑长任务，复用连接。
3. **多租户 SaaS 平台**：需要按租户切库，需要观测面板。

## 3. 用户场景

### 3.1 Web 后端

| 场景 | 痛点 | 期望 |
| :--- | :--- | :--- |
| 同步查询用户列表 | 没有慢 SQL 视角 | Top SQL / 慢 SQL |
| 偶发 `DROP TABLE` 误执行 | 只能依赖权限 | Wall 拦截 |
| 长尾连接超时 | 缺少连接获取延迟 | 池获取 P95 指标 |

### 3.2 后台 worker

| 场景 | 痛点 | 期望 |
| :--- | :--- | :--- |
| 长任务占用连接 | 没有泄漏检测 | `Drop` 自动归还 + 持有时长告警 |
| 大量重复 SQL（按字段） | 没有合并视角 | SQL 合并 + 指纹 |
| 多线程并发读 | 池满排队 | `acquire_timeout` 返回 |

### 3.3 多租户 SaaS

| 场景 | 痛点 | 期望 |
| :--- | :--- | :--- |
| 主库故障切备库 | 切库需要侵入业务代码 | 多数据源切换 |
| 读写分离 | 没有标准抽象 | `SqlHint::Read` 路由到从库 |
| 故障定位 | 缺少统一监控端点 | `/druid/api/*` JSON |

## 4. 现有方案调研

### 4.1 sqlx 现状

- 提供 `sqlx::Pool` 与 `sqlx::Connection`。
- 无横切层；监控需自行用 `tracing` + 自定义中间件。
- 没有 Wall / SQL 合并 / 多数据源。

### 4.2 deadpool 现状

- 提供 `deadpool::managed::Pool`。
- 与 sqlx 集成需要 `sqlx` adapter；生态不统一。
- 没有横切层。

### 4.3 bb8 现状

- 提供 `bb8::Pool`。
- 与 sqlx 集成需 `sqlx-bb8` crate。
- 没有横切层。

### 4.4 rbatis / rbdc 现状

- 提供 `rbdc::Pool` + `rbdc::Connection`，跨 6 个数据库。
- 自实现 wire protocol；体积与维护成本较高。
- 没有横切层与 Wall。
