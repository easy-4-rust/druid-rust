### 本文档执行责任

本文只回答三件事：**先做什么、按什么顺序做、做到什么程度算完成**。逐对象事实归 [对象级对照表](对象级对照表.md)，能力语义归 [语义迁移对照表](语义迁移对照表.md)，命名与路径归 [对象名称一致性检查](对象名称一致性检查.md)。任何阶段完成都必须同时满足：对象台账无新增未完成项、对应语义行有可观察测试、覆盖率与差分证据已归档。

## 与当前代码的核对结论（本轮审计）

1. **对象层**：Java `core` 共 1875 个对象；同名命中 129 个（全部为 `UNVERIFIED`，只证明名字存在），缺失 1746 个，其中 1415 个属于解析器族（AST/dialect/visitor/parser）的**登记替换**，真正待实现 331 个。
2. **方法层**：Java 公开方法 20476 个；Rust 同名 snake_case 候选 470 个。该数字**低估**真实迁移度（Rust 大量使用语义族合并、默认方法与 `*_with_*` 后缀），但也说明不能以“同名”作为完成证据。
3. **测试层**：Java 3558 个测试文件 / 4758 个 `@Test`；Rust 431 个 `tests/` 文件 / 4534 个测试属性。数量接近，但**逐用例差分覆盖仍未闭合**（`status.md`：固定 59 例中 10 项差异、Task6 FIX_REQUIRED）。
4. **结构层**：产品源码 862 文件 / 137,391 行；**25 个文件超过 800 行阻断线**、47 个处于 501–800 行复核区、**65 个文件含多个公开对象**。这三项按技能规则直接阻断“迁移完成”结论。
5. **架构层**：当前代码符合 ADR-CRATE-002（`druid-rdbc` 只放 JDBC 标准合同，核心逻辑在 `druid`）；但**与最新用户指令（核心逻辑进 `druid-rdbc`、`druid` 退化为门面）冲突**，必须先形成 ADR-CRATE-003 再动代码，禁止边写边改边界。
6. **本轮已执行**：修复 `SEM-POOL-001` 的 FIFO/LIFO 语义偏差（Java `pollLast` 为 LIFO），新增 `crates/druid/tests/pool_idle_reuse_order_test.rs` 并实测通过；覆盖率基线见“P6”。

## P2 解析器保真决策（已启动：Rust 观测完成）

P2 已启动，四方言 Rust 观测见 [dialect-fidelity/README.md](dialect-fidelity/README.md)：Oracle 7/8、ODPS 8/8、Hive 7/8、Doris 6/8（parse→format→reparse）。Java golden 列仍为 `PENDING`，需固定 jar 生成后替换；在此之前不得把矩阵当作方言保真通过证据。


现状：Java 31 个方言 / 423 个 AST 类 / 405 个 visitor 方法，被 `sqlparser 0.52` 的 10 个方言族替代；1415 个对象因此处于 `MISSING + REPLACED_DEPENDENCY`。

| 选项 | 内容 | 代价 | 风险 |
|---|---|---|---|
| A | 接受替换，建立“方言保真矩阵”，用 Java corpus 做 parse/format/parameterize/wall 四列 golden diff | 中 | Druid 特有语法（Oracle PL/SQL、ODPS、Hive/Doris）覆盖不足 |
| B | 在 `druid` 内恢复 Druid 自研 Lexer/AST 子集（仅高频方言） | 高 | 双解析器并存，维护成本翻倍 |
| C | 混合：sqlparser 负责通用 SQL，Druid 负责方言扩展与 wall 规则 | 中高 | 边界与错误语义需严格定义 |

**建议**：A + C 的组合——先 A 建立证据，再对证据不足的 3–5 个方言按 C 增补扩展点。**在 ADR 批准前，不得把解析器族对象标记为 `DEPENDENCY_REUSED`**（缺少逐符号证据）。

## P3 Crate 职责重切（ADR-CRATE-003，待批准）

用户目标：`druid-rdbc` 承载“RDBC API + Druid 核心逻辑 + 全部接口”，`druid` 退化为门面；`druid-wrapper` 承载全部真实驱动整合；`druid-metrics` 负责采集上报；`druid-admin` 为独立带静态前端的后端；`druid-bench` 只做验证。

与现状的冲突：ADR-CRATE-002（ACCEPTED）把 Pool/Filter/SQL/Wall/Stat/Dynamic 放在 `druid`，且明确禁止 `druid-rdbc → druid` 反向依赖。

**分期方案（每期可独立回滚）**：

| 期 | 动作 | 不改什么 | 退出条件 |
|---|---|---|---|
| P3.1 | 在 `druid-rdbc` 内新增 `governance/` 模块，仅依赖标准合同，承载**与驱动无关**的池策略/统计/熔断算法 | 不移除 `druid` 现有实现 | 新模块单测 + 属性测试通过，`cargo tree` 无 `druid` 依赖 |
| P3.2 | `druid` 的 Pool/Stat 改为调用 `druid-rdbc::governance`，保留类型别名与兼容路径 | 不删除公共 API | `druid::sql::*` 消费者编译测试通过 |
| P3.3 | 把 Filter/Wall 的**接口**移入 `druid-rdbc`，实现留在 `druid` | 不动 sqlparser | 迁移前后的差分用例 MATCH |
| P3.4 | `druid` 只保留门面/重导出 | 不动 wrapper | public-api 快照与 SemVer 报告归档 |

前置条件：先修 P1，再启动 P3.1；否则会把未稳定的语义搬进新边界。

**状态**：ADR-CRATE-003 已于 2026-10-22 批准，P3 启动；P3.1 的首批对象限定为“纯函数策略”（等待公平性、淘汰判定、统计聚合），不改运行时所有权。

## P4 dbx 借鉴：编译期分发与 2PC（设计后实现）

| 目标 | dbx 做法 | druid-rust 落地设计 | 门禁 |
|---|---|---|---|
| 消除 trait object 动态开销 | 枚举 + 宏统一 20+ 异构池入口 | 在 `druid-rdbc` 增加 `DriverKind` 枚举与 `dispatch!` 宏，生成 `exec/fetch/metadata` 的静态分支；trait object 仅保留在外部扩展点 | 宏展开后无 `dyn` 调用；基准对比 p99 不退化 |
| 2PC + 崩溃恢复 | 持久化事务日志 `2pc:tx:{id}`，Mixed 态不重新 commit | 在 `druid-rdbc` 定义 `TwoPhaseCommit` 与 `TxLogStore`（append-only、幂等 replay）；状态机 `Prepared/Committed/Aborted/Mixed`，Mixed 只做只读探测与人工/策略裁决 | 崩溃注入测试：重启后状态可重建；Mixed 绝不重发 commit |
| 78 种数据库对接 | catalog + 统一执行入口 | 现有 80-profile manifest 复用；把 `runtimeMode` 映射到 `DriverKind` 的分发实现 | 每个 profile 至少一个合同测试，未验证不得升级状态 |

**范围控制**：P4 先做 3 个驱动族（sqlx / toasty / jdbc-agent）的静态分发原型，再推广；2PC 先在 SQLite/PostgreSQL 上做日志与恢复演练，不承诺全驱动。

## P5 Metrics/Admin：独立服务 + 静态前端（对齐用户目标）

基于 `agent-job-admin` 的调研结论：

| 决策 | 选择 | 理由 |
|---|---|---|
| 前端打包 | `rust-embed`（或 `include_dir!`）内嵌静态资源 | agent-job 用 `CARGO_MANIFEST_DIR` 运行时读盘，二进制不可搬迁；druid-admin 必须单文件可部署 |
| 采集通道 | `druid-metrics` 采样 → **有界** mpsc → 聚合 → gRPC 单协议 | SQL 热路径绝不 `send().await`；沿用 ADR-RUNTIME-001 |
| admin 通信 | 复用 `druid_metrics.v1` 双向流；ACK 窗口存完整 frame，断线重连按 sequence resync | 已有协议，禁止第二份 proto |
| 鉴权 | 默认 loopback；远程必须 TLS + 认证；cookie 使用签名 session（不沿用 agent-job 的明文 username） | agent-job 的 cookie 可伪造，不可照搬 |
| 背压 | 有界队列 + `Semaphore` 准入 + 明确的 drop/coalesce 策略 | 对齐 ADR-RUNTIME-001 与 agent-job 的 `AdmissionGate` 优点 |

退出条件：单二进制启动后 `/druid/*` 与 `/api/*` 可用；断网重连后 sequence 无缺口；压测下采集通道 `queue_full` 可观测且不阻塞 SQL。

**进度**：B1 第一批已拆 `filter_defaults_chain_harness` 与 `log_filter`，超 800 行文件 28 → 26（本页快照随台账自动更新）。
