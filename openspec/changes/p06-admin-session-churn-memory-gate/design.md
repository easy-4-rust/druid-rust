# Design

The new integration test is its own binary so other Admin test allocations cannot distort the sampled process-memory baseline. It uses the real `MetricsRepository` and `ServiceIdentity`, not mocks. Each generation atomically admits 32 distinct boot identities with two datasource IDs, then waits 250 ms before the next generation; the configured TTL is 200 ms. The test samples process physical memory before and after every generation, plus a final sample. The same `memory_stats` probe already used by the Admin capacity gate provides platform-specific RSS or working set.

The workload is 50 × 64 accepted projections, each carrying a 60 KiB SQL string. It cumulatively allocates about 188 MiB of SQL projection text while retaining only the current generation's roughly 3.8 MiB. It checks exact live count, previous-generation invisibility, expected TTL eviction count and zero capacity rejections. The 128 MiB ceiling is the existing Admin sampled physical-memory ceiling; the result is explicitly a sampled high-water mark rather than a lifetime OS peak. Insertion p50/p95/p99 are emitted for subsequent baseline analysis but are not used as a flaky hosted-runner latency gate.

No new dependency or product behavior is required. Normal `cargo test -p druid-admin --locked` automatically includes the new integration target; the existing Rust-contracts CI job exercises it on Windows, macOS and Linux.
