# Design

Use existing executable integration tests as fault injectors. Emit one stable, structured summary only after each scenario's behavior assertions pass. A Python runner locates the exact Cargo test executable from JSON build output, reruns the named test, captures stdout/stderr and Linux child peak RSS, computes nearest-rank p50/p95/p99, and writes a JSON record before rejecting missing data or a budget violation. Reuse the established `runtime-benchmark` scheduled/manual workflow and upload partial logs on failure.

For Pool, the blocked physical close scenario reports queue peak, rejected closes, close timeouts, completed physical closes, and shutdown duration. The fault must actually saturate the queue; a zero rejection or over-capacity queue invalidates a run. For Admin, retain existing network scenarios for unavailable/restart, duplicate batch, sequence gap, invalid authentication, and pending-ACK SIGTERM. Their numeric acceptance must use real process/network observations rather than repository-only simulations. Metrics saturation and JDBC Agent handshake/frame guards already have dedicated gates and remain referenced, not duplicated.

Do not set a new latency or RSS ceiling from an unmeasured guess. Commit the instrumentation and runner as a coding milestone, then gather baseline data and set numeric limits in a separate coding milestone before final module-wide testing and archive. The user's requested test order supersedes per-edit TDD execution; write checks with the implementation and run them in the later module batch.
